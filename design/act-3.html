Act 3 — Power User

Six scenes: session history, review, states, commit, project overview, and multi-project. Canvas becomes your workshop.

Job to be done: Work across parallel sessions without conflicts, stay informed without interruption, and accumulate project-level memory that persists across sessions.
You’ve been using Canvas for a while now. The terminal is comfortable. The viewer is useful. But you’re starting to push harder — multiple sessions on the same project, long-running tasks in the background, context you need to remember across days. This is where Canvas transitions from utility to infrastructure. Sessions stop being ephemeral terminal instances and become meaningful units of work with identity, history, and memory.

Scene 3.1 — Session History Overview

You look at the sidebar and see the full story of your project’s sessions. CANVAS-APP has four sessions: two completed (green checkmarks), one failed (red dot), and one currently running (amber dot). Each row shows the session name, status, duration, and worktree badge. The sidebar is the index — a glanceable record of everything that’s happened.

The sidebar is the session ledger. At a glance you know: what’s done, what’s running, what broke. Green/amber/red/gray dots create an instant attention hierarchy — your eye goes to the failure first, then the running session, then the completed work. No hunting through terminal history.

Scene 3.3 — Session States

Three variants showing how the SUMMARY tab adapts to each session state. Done (green): happy path with “All tests passing.” Failed (red): the session broke — the trail explains why. Stale (gray): the session was abandoned days ago — the trail shows where it stopped.

Each state has a distinct visual weight. Green is calm — everything’s fine. Red is loud — something needs attention. Gray is neutral — not alarming, just “hey, this is incomplete.” The SUMMARY tab adapts its status line and tone to match. The user always knows the session’s state before reading a single line of detail.

Scene 3.4 — Commit & Push

You commit from the terminal: git add -A && git commit, git push, gh pr create. Canvas doesn’t interfere — this is your CLI workflow. But the SUMMARY tab updates to surface the result: PR #47 opened, CI status, commit hash, file diff summary. The changes section lives inside SUMMARY, not as a separate tab — because what you committed is part of the session’s story.

Canvas is additive, not replacement. You commit the way you’ve always committed. But Canvas shows you what you committed in a structured view — no need to open GitHub to check CI status. The CLI does the action. Canvas shows the receipt. Changes belong in SUMMARY because they’re the session’s output, not a separate concern.

Scene 3.5 — Project Overview

You click the project name (“CANVAS-APP”) in the sidebar. The main area transforms into a project-level view. OVERVIEW tab: AI assessment banner, project vision, structured outcomes from OUTCOMES.md with status badges. STATS tab: 2×2 aggregate grid (sessions, time, tokens, files) and LLM-generated insights for velocity, alignment, efficiency, and risk. This is where the flywheel becomes tangible.

Projects have identity. The overview is the project’s home page — what’s the vision, what are the outcomes, what’s the status. Stats turn invisible work into visible patterns — no developer tracks their token efficiency across sessions. Canvas sees what you can’t because it has the data and the model to interpret it.

Scene 3.6 — Multi-Project

You have three projects in the sidebar: CANVAS-APP (expanded, one running session), team-pulse (collapsed, showing “3 sessions”), and budget-tracker (collapsed, “1 session”). You click team-pulse — it expands, Canvas switches context. Each project is its own world with its own sessions, history, and memory. Switching feels like opening a different notebook.

Multiple projects in one workspace is the natural end state for power users. The sidebar handles this with expand/collapse: the active project takes space, inactive projects are one line each. No separate “project switcher” or modal. The sidebar IS the project switcher. Workspace stays clean because only one project is expanded at a time.
